func expandSSHKeys(input []interface{}) []virtualmachines.SshPublicKey {
    output := make([]virtualmachines.SshPublicKey, 0)

    for _, v := range input {
        raw := v.(map[string]interface{})

        username := raw["username"].(string)
        output = append(output, virtualmachines.SshPublicKey{
            KeyData: pointer.To(raw["public_key"].(string)),
            Path:    pointer.To(formatUsernameForAuthorizedKeysPath(username)),
        })
    }

    return output
}

func formatUsernameForAuthorizedKeysPath(username string) string {
    return fmt.Sprintf("/home/%s/.ssh/authorized_keys", username)
}

## Critical Review & Edge Case Analysis

### Null Semantics

- `var.admin_ssh_key == null`: The entire SSH configuration is omitted from linuxConfiguration
- `key.username == null`: Not possible due to Required constraint in schema
- Empty set `[]`: Would result in an empty array `[]` in publicKeys (handled correctly)

### Empty String Username

- The provider's `ValidateFunc: validation.StringIsNotEmpty` prevents empty strings
- Our implementation assumes non-empty username (safe due to validation)
- If somehow an empty string got through, path would be `/home//.ssh/authorized_keys` (invalid but caught by Azure API)

### Special Characters in Username

- Linux usernames have restrictions (alphanumeric, dash, underscore)
- Provider validation (LinuxAdminUsername) ensures valid username format
- No escaping needed in path - username characters are safe for string interpolation
- Azure API validates the username format

### Path Format Consistency

- Provider always uses `/home/{username}/.ssh/authorized_keys`
- No variation in format (not `/root/.ssh/authorized_keys` for root user, etc.)
- This is the standard Linux convention for non-root users
- Our implementation exactly matches this format

### Username Uniqueness

- TypeSet with hash function ensures no duplicate username+public_key combinations
- If same username appears with different public_keys, it would be a schema violation at the Terraform level
- Azure API would accept multiple keys for the same username (last one wins or error)
- Not a concern for our implementation - Terraform schema handles this

### Safe References

- All nested access uses `key.username` from the `for` expression
- The `for` expression only executes when `var.admin_ssh_key != null` (conditional check)
- `local.effective_ssh_keys` is guaranteed to have both `username` and `public_key` properties

### Idempotency

- Path computation is deterministic: same username always produces same path
- No order dependency
- No state dependency (other than the username value itself)
- Matches provider's behavior exactly

The implementation integrates seamlessly with Task #57's work:

- Both `keyData` and `path` are in the same object within the `for` expression

### Read Operation Behavior

From the provider's flatten function, the username is **derived from the path** during read:
```go
username := strings.TrimPrefix(strings.TrimSuffix(v.Path, "/.ssh/authorized_keys"), "/home/")
```

This means:
- Provider writes: `/home/{username}/.ssh/authorized_keys`
- Azure API stores: `/home/{username}/.ssh/authorized_keys`
- Provider reads: extracts username from path
- Round-trip is consistent

Our implementation maintains this consistency by always computing the same path from username.
