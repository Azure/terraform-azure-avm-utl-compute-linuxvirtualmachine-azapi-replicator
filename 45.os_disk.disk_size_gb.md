## Special Handling

### Validation

**From Provider Schema:**
```go

**Implementation in variables.tf:**

validation {
  condition = (
    var.os_disk == null ||

    (var.os_disk.disk_size_gb >= 0 && var.os_disk.disk_size_gb <= 4095)
  )
  error_message = "disk_size_gb must be between 0 and 4095."
}
```

**Rationale:** The validation ensures the disk size is within Azure's supported range for OS disks (0 to 4095 GB). The condition handles null values gracefully since the field is optional.

### Conditional Assignment Logic

**From Provider Expand Function:**
```go
if osDiskSize := raw["disk_size_gb"].(int); osDiskSize > 0 {
    disk.DiskSizeGB = pointer.To(int64(osDiskSize))
}
```

**Key Behavior:** The provider only assigns `DiskSizeGB` when the value is greater than 0. When the value is 0 or not provided, the field is not set (remains nil), allowing Azure to use the default disk size from the image.

**Implementation:**
```hcl
diskSizeGB = var.os_disk.disk_size_gb != null && var.os_disk.disk_size_gb > 0 ? var.os_disk.disk_size_gb : null
```

**Rationale:** This exactly replicates the provider's conditional logic:
- When `disk_size_gb` is `null` → `diskSizeGB = null` (not set)
- When `disk_size_gb` is `0` → `diskSizeGB = null` (not set, provider behavior)
- When `disk_size_gb` is `> 0` → `diskSizeGB = value` (explicit size)

### ForceNew

The field does NOT have `ForceNew: true` in the schema, meaning disk size changes can be applied via update operations without recreating the VM. Therefore, no entry is needed in `replace_triggers_external_values`.

### Computed Behavior

The field has `Computed: true` because Azure may return a default disk size when creating a VM from an image, even if `disk_size_gb` is not specified. Our implementation handles this by:
- Allowing null values (optional field)
- Not forcing a specific default value
- Letting Azure determine the disk size when not explicitly set

## Critical Review & Edge Cases

### Edge Case Analysis

1. **Null Semantics:**
   - `disk_size_gb = null` → `diskSizeGB` not sent to API → Azure uses image default size
   - This is correct behavior matching provider intent

2. **Zero Value:**
   - `disk_size_gb = 0` → `diskSizeGB` not sent to API (filtered by `> 0` check)
   - Matches provider's expand logic exactly
   - Validation allows 0, but expand function filters it out
   - This creates consistency with provider behavior where 0 means "use default"

3. **Boundary Values:**
   - Minimum: 0 (validated, but treated as null in API)
   - Maximum: 4095 (validated, matches Azure limit)
   - Both boundaries are correctly validated

4. **Idempotency:**
   - First apply with `disk_size_gb = 100` → Creates disk with 100GB
   - Subsequent applies with same value → No change
   - Subsequent applies with different value → Updates disk size (no ForceNew)
   - Idempotent because value is directly assigned without transformations

5. **Safe References:**
   - `var.os_disk.disk_size_gb` - Safe because parent `var.os_disk != null` check exists in skeleton
   - No nested object access beyond validated level

6. **Update Behavior:**
   - Field supports updates (no ForceNew)
   - Azure allows disk size increases but not decreases
   - Provider allows the change; Azure API enforcement handles restrictions
   - This matches provider behavior (no validation against decreases in Terraform)

7. **Computed Field Interaction:**
   - Field is Computed in provider (Azure may set default)
   - Our implementation doesn't force a default, allowing Azure's behavior to persist
   - When reading state, Azure returns actual disk size even if not specified
   - This is correct handling of Optional+Computed pattern
