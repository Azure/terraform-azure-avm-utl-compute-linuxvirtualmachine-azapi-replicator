## Critical Review & Edge Case Analysis

### Null Semantics
- **`var.zone = null`:** Zone is not specified, VM has no zone pinning (regional deployment)
- **Meaning:** "Do not assign to any specific availability zone" (default behavior)
- **API behavior:** When `zones` is `null` or empty, Azure deploys the VM regionally without zone pinning

### Edge Cases

1. **Empty string:** Not a valid zone - users should set to `null` instead. Terraform validation in variables.tf should prevent empty strings.

2. **Single zone vs. multiple zones:** Azure VMs support only a single zone. The API field is a list for consistency with other resources (like scale sets), but VMs can only specify one zone. The provider enforces this with `ZoneSingleOptionalForceNew()`.

3. **Zone format:** Azure zones are typically "1", "2", "3" (string representations of numbers). The common schema validates the format.

4. **Conflict resolution:** The existing validation in variables.tf ensures `zone` and `availability_set_id` cannot both be set, as they are mutually exclusive deployment models.

### Idempotency

✅ Implementation is idempotent:
- `var.zone = "1"` → `zones = ["1"]` (consistent)
- `var.zone = null` → `zones = null` (consistent)
- No order dependencies since it's a single value

### Safe References

✅ All references are safe:
- Direct variable access `var.zone` (no nested access)
- Null check before array construction: `var.zone != null ? [var.zone] : null`
- No risk of accessing null/undefined properties

### API Behavior Consistency

- Both produce identical API payload
