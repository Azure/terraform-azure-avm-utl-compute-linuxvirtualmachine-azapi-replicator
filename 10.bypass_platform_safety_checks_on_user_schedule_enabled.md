### Issues Identified

#### Issue 1: Shallow Merge Vulnerability for Shared Path

**Problem:**
The original implementation added `linuxConfiguration` as a conditional element in the `osProfile` merge without using nested merge. While this doesn't cause an immediate problem (only one occurrence currently), it violates executor.md's requirement for shared paths and would fail when future tasks add more `linuxConfiguration` fields (e.g., Task #16 `disable_password_authentication`, Task #26 `patch_mode`, Task #31 `reboot_setting`).

**Executor's Implementation:**
```hcl
osProfile = merge(
  { adminUsername = ... },
  { allowExtensionOperations = ... },
  var.bypass... ? { linuxConfiguration = { patchSettings = {...} } } : {}
)
```

**Why This Violates executor.md:**
From executor.md line 132:
> ⚠️ `merge()` is SHALLOW! Use nested `merge()` for shared paths

When Task #16 or other tasks add their own `linuxConfiguration` objects, the shallow merge would cause the later occurrence to overwrite the earlier one, resulting in data loss.

**Provider's Actual Behavior:**
Provider accumulates all `linuxConfiguration` fields into a single nested object. Multiple fields like `disablePasswordAuthentication`, `patchSettings.automaticByPlatformSettings`, etc., coexist within the same `linuxConfiguration` object.

**Expected Behavior:**
- All `linuxConfiguration` fields from different tasks should be merged together using nested merge
- The `linuxConfiguration` key should appear only ONCE in the `osProfile` merge
- Child fields within `linuxConfiguration` should be merged in a nested merge statement

**Root Cause:**
Executor added `linuxConfiguration` as a top-level conditional element without preparing for future fields that will share the same parent path.

### Corrections Made

#### Fix 1: Nested Merge for linuxConfiguration

- `migrate_main.tf`: Restructured `osProfile` merge to use nested merge for `linuxConfiguration`
