## Special Handling

### ForceNew Behavior

The `location` field has `ForceNew: true` in the provider schema (via commonschema.Location()). This means any change to the location requires resource replacement.

**Implementation:**
```hcl
replace_triggers_external_values = {
  location = { value = var.location }
}
```

The value is wrapped in an object to ensure the key remains stable. The full value is tracked to detect any changes.

### Location Normalization

**Provider Behavior:** The azurerm provider normalizes location strings using `location.Normalize()`, which:
1. Converts to lowercase
2. Removes spaces and special characters
3. Converts display names to canonical names (e.g., "East US" → "eastus")

**AzAPI Behavior:** The azapi provider (v2.0+) handles location normalization internally when comparing values. We pass the location directly from `var.location` to `azapi_header.location` without manual normalization.

**DiffSuppressFunc:** The provider uses `commonschema.Location()` which includes a DiffSuppressFunc that makes location comparisons case-insensitive and handles various formatting differences. The azapi provider's internal handling of location fields provides equivalent behavior.

### Validation

The provider schema for location (via `commonschema.Location()`) does **not** include explicit validation - Azure validates location names server-side. The provider accepts any string value and relies on the Azure API to reject invalid locations.

**No validation needed in variables.tf** - The existing variable definition is sufficient. Azure will validate that the location is a valid region during the API call.

## Critical Review & Edge Case Analysis

### Null Semantics

- **Variable:** `nullable = false` - the location must always be provided
- **Required:** Yes, this is a required argument
- **Meaning:** Location cannot be null; it must be a valid Azure region string

### Boundary Conditions

- **Empty string:** Would be rejected by Azure API (not a valid location)
- **Invalid location name:** Azure API validates and returns error if location doesn't exist
- **Case variations:** Handled by azapi provider's internal normalization (e.g., "EastUS", "eastus", "East US" are equivalent)
- **Display names vs canonical names:** Both accepted; azapi normalizes internally

### Idempotency

- The location is a simple string value with no order-dependent behavior
- ForceNew ensures that any change to the location creates a new resource (idempotent)
- No array operations or merge logic involved
- Location normalization by azapi ensures "East US" and "eastus" are treated as the same value (no spurious diffs)

### Safe References

- Direct reference to `var.location` is safe as it's a required, non-nullable field
- No nested property access required
- No risk of null pointer exceptions

### Edge Cases

1. **Case sensitivity:** Azure locations are case-insensitive. The azapi provider handles normalization internally, so "eastus", "EastUs", and "EASTUS" are all treated equivalently.

2. **Display name vs canonical name:** Users might provide "East US" (display name) or "eastus" (canonical name). The azapi provider normalizes both forms, preventing false change detection.

3. **Spaces and special characters:** Display names may include spaces (e.g., "East US"). The azapi provider's location normalization removes spaces for comparison purposes.

4. **Location availability:** Not all Azure locations are available in all subscriptions or for all resource types. Azure API will validate availability and return appropriate errors.

5. **Cross-region dependencies:** Some resources (like network interfaces) must be in the same region as the VM. This is validated by Azure API during creation.

6. **Location change behavior:** Since location has ForceNew, any change triggers complete resource replacement. Users cannot change the location of an existing VM - they must create a new one.
