## Critical Review & Edge Cases

### Edge Case Analysis

**1. Null Semantics:**
- Default value is `-1` (explicit default, not null)
- Variable has `nullable = false` to enforce that a value is always present
- When value is `-1` or `<= 0`, billingProfile is `null` (not sent to API)
- When value is `> 0`, billingProfile object is created with maxPrice

**2. Boundary Conditions:**
- Value exactly `-1`: Valid, means no eviction for price (default behavior)
- Value exactly `0`: Valid per validation, but provider logic (`v > 0`) means billingProfile not sent
- Value `0.0001`: Valid, billingProfile will be sent
- Negative values less than `-1`: Invalid, blocked by validation
- Very large values: Accepted if >= -1, Azure API will validate business rules

**3. Priority Dependency:**
- Validation ensures max_bid_price can only be configured when priority is "Spot"
- If priority is not "Spot" and max_bid_price > 0, validation fails at plan time
- If priority is "Regular" and max_bid_price is -1 or 0, validation passes (no-op)

**4. Idempotency:**
- Value comparison is straightforward (float equality)
- No order-dependent operations
- Conditional rendering (`> 0`) is deterministic and idempotent

**5. Safe References:**
- Direct variable reference, no nested access needed
- No null pointer concerns due to `nullable = false`

**6. Update Behavior:**
- Not ForceNew, but requires deallocation
- azapi_resource will attempt in-place update
- If VM is running, Azure API will return error requiring deallocation
- This matches provider behavior where deallocation is handled automatically

**7. Default vs Explicit Zero:**
- Default `-1` means "no eviction for price"
- Explicit `0` means "evict at any price" (rarely used)
- Both `-1` and `0` result in `null` billingProfile (conditional `> 0`)
- Only positive values create billingProfile in API payload
