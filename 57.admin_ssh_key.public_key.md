## Special Handling

### DiffSuppressFunc Implementation

The provider has a `DiffSuppressFunc: suppress.SSHKey` that normalizes SSH keys before comparison:

```go
func SSHKey(_, old, new string, _ *pluginsdk.ResourceData) bool {
    oldNormalized, err := NormalizeSSHKey(old)
    if err != nil {
        log.Printf("[DEBUG] error normalising ssh key %q: %+v", old, err)
        return false
    }

    newNormalized, err := NormalizeSSHKey(new)
    if err != nil {
        log.Printf("[DEBUG] error normalising ssh key %q: %+v", new, err)
        return false
    }

    if *oldNormalized == *newNormalized {
        return true
    }

    return false
}

func NormalizeSSHKey(input string) (*string, error) {
    if input == "" {
        return nil, fmt.Errorf("empty string supplied")
    }

    output := input
    if strings.HasPrefix(output, "<<~EOT") && strings.HasSuffix(output, "EOT") {
        output = strings.TrimPrefix(output, "<<~EOT")
        output = strings.TrimSuffix(output, "EOT")
    }
    output = strings.ReplaceAll(output, "\r", "")

    lines := make([]string, 0)
    for _, line := range strings.Split(output, "\n") {
        lines = append(lines, strings.TrimSpace(line))
    }

    normalised := strings.Join(lines, "")

    return pointer.To(normalised), nil
}
```

**Normalization Logic:**
1. Remove heredoc markers (`<<~EOT` prefix and `EOT` suffix)
2. Remove all carriage returns (`\r`)
3. Split by newlines, trim whitespace from each line
4. Join all lines into a single string

**Implementation in Terraform:**

Following the DiffSuppressFunc pattern from diffsuppressfunc.md, I implemented:

1. **Normalization function** (`local.normalize_ssh_key`): Creates a map of username → normalized key for all input keys
2. **Read existing state**: Fetches existing SSH keys from `data.azapi_resource.existing.output.properties.osProfile.linuxConfiguration.ssh.publicKeys`
3. **Create lookup map** (`local.existing_ssh_keys_by_username`): Parse username from path and map to keyData
4. **Effective value selection** (`local.effective_ssh_keys`): For each key, normalize both old and new, compare, and use existing if they match
5. **Body assignment**: Use `local.effective_ssh_keys` which contains the effective values

**Key Implementation Details:**
- When normalized keys match, we use the existing key value to suppress the diff
- When they don't match, we use the new key value
- When no existing key exists for a username, we use the new key value
- The normalization exactly replicates the provider's NormalizeSSHKey function

- In our implementation, an empty string would normalize to an empty string and be compared accordingly

### Carriage Returns and Line Breaks
- The normalization handles `\r` and `\n` characters
- Heredoc syntax (`<<~EOT`...`EOT`) is properly stripped
- Multiple lines are trimmed and joined into a single string

### Normalization Comparison
- Both old (existing) and new (desired) keys are normalized using the same logic
- If normalized versions match, we use the existing key to suppress the diff
- This prevents unnecessary resource replacement when only formatting differs

### Username Matching
- Keys are matched by username using `local.existing_ssh_keys_by_username`
- The username is parsed from the existing key's path (`/home/{username}/.ssh/authorized_keys`)
- If a username doesn't exist in the current state, the new key is used
- If a username exists but the normalized key differs, the new key is used

### Safe References
- All nested access uses conditional checks and `try()` with fallbacks
- `local.effective_ssh_keys` is only built when `var.admin_ssh_key != null`
- `lookup()` with default values prevents null reference errors

### Idempotency
- The normalization ensures that functionally equivalent SSH keys (with different formatting) are considered the same
- Using the existing key value when normalized keys match ensures idempotent operations
- The `for` expression over the set produces deterministic output

### ForceNew Behavior
- Since the entire `admin_ssh_key` set is ForceNew, any change (add/remove/modify keys) triggers replacement
- Tracking `var.admin_ssh_key` directly captures all changes to the set
- The DiffSuppressFunc only affects diff display, not the ForceNew behavior when keys actually change

### Issues Identified

#### Issue 1: Incorrect Heredoc Marker Removal Logic

**Problem:**
The executor's DiffSuppressFunc normalization logic used `replace()` to remove heredoc markers, which removes ALL occurrences of "<<~EOT" and "EOT" anywhere in the string, not just at the beginning and end.

**Executor's Implementation:**
```hcl
normalize_ssh_key = { for key_input in ... : key_input.username => (
  join("", [for line in split("\n", replace(replace(
    replace(replace(key_input.public_key, "<<~EOT", ""), "EOT", ""),
  "\r", ""), "\n", "\n")) : trimspace(line)])
) }
```

**Why This Violates executor.md:**
The provider uses `strings.TrimPrefix()` and `strings.TrimSuffix()` which ONLY remove markers at the start and end:
```go
if strings.HasPrefix(output, "<<~EOT") && strings.HasSuffix(output, "EOT") {
    output = strings.TrimPrefix(output, "<<~EOT")
    output = strings.TrimSuffix(output, "EOT")
}
```

**Provider's Actual Behavior:**
- If SSH key contains "EOT" in the middle (e.g., "ssh-rsa AAAA...EOT...BBBB"), provider leaves it untouched
- Only removes "<<~EOT" prefix and "EOT" suffix when BOTH are present

**Expected Behavior:**
- Input: `"<<~EOT\nssh-rsa AAAA...EOT...BBBB\nEOT"` → Output: `"ssh-rsa AAAA...EOT...BBBB"` (middle "EOT" preserved)
- Input: `"ssh-rsa AAAA...EOT...BBBB"` → Output: `"ssh-rsa AAAA...EOT...BBBB"` (no markers, unchanged)

**Root Cause:**
Executor used `replace()` which performs global replacement instead of prefix/suffix-specific removal. This causes incorrect normalization when "EOT" appears in the SSH key content itself.

#### Issue 2: Redundant Replace Operation

**Problem:**
The normalization logic included `replace(..., "\n", "\n")` which replaces newlines with newlines - a no-op that serves no purpose.

**Why This Violates executor.md:**
The executor added unnecessary operations not present in the provider's logic. While this doesn't cause incorrect behavior, it violates the principle of EXACT replication (no additions, no simplifications).
