# Task #24 - os_managed_disk_id

## Summary

Implemented `os_managed_disk_id` as a root-level Optional argument with ForceNew behavior. When set, the field attaches an existing OS managed disk to the VM instead of creating a new disk from an image. The field has ExactlyOneOf relationships with `admin_username`, `source_image_id`, and `source_image_reference`, and ConflictsWith multiple osProfile-related fields. When `os_managed_disk_id` is set, the OS disk createOption changes from "FromImage" to "Attach", and the managedDisk.id is set to the provided disk ID.

## Create Phase Verification

### Pattern Identification

Based on the provider source code analysis, when `os_managed_disk_id` is set:

1. **Create Phase:** Single-phase operation - the field is set during the primary `CreateOrUpdate` call
2. **Update Phase:** The field is ForceNew, so it cannot be updated (triggers replacement)
3. **Field Classification:** Primary create field (not post-creation)

**Evidence from provider behavior:**

When `os_managed_disk_id` is set, the provider:
- Sets `osDiskIsImported = true`
- Changes `CreateOption` from `"FromImage"` to `"Attach"`
- Sets `managedDisk.ID` to the provided disk ID
- Skips sending `osProfile` (since admin_username cannot be set with os_managed_disk_id)
- Skips fields like `storageAccountType`, `name`, `diskSizeGB` for the managed disk (these are read from the existing disk)

**Decision:** Implement in `local.body.properties.storageProfile.osDisk` with conditional logic based on `var.os_managed_disk_id != null`.

## Assignment Path Verification

### Predicted Path

`body.properties.storageProfile.osDisk.managedDisk.id` (when os_managed_disk_id is set)
`body.properties.storageProfile.osDisk.createOption` changes to `"Attach"`

### Go Code Evidence

From provider Create method:

```go
// Determine if we're attaching an existing OS disk
existingDiskId, _ := pluginsdk.GoValueFromTerraformValue[string](d.GetRawConfig().AsValueMap()["os_managed_disk_id"])
osDiskIsImported := existingDiskId != ""

// Build OS disk structure
osDisk := &virtualmachines.OSDisk{
	Caching: pointer.To(virtualmachines.CachingTypes(d.Get("os_disk.0.caching").(string))),
	Name:    pointer.To(diskName),
	OsType:  pointer.To(virtualmachines.OperatingSystemTypesLinux),
}

// Set create option based on whether disk is imported
if osDiskIsImported {
	osDisk.CreateOption = pointer.To(virtualmachines.DiskCreateOptionTypesAttach)
	osDisk.ManagedDisk = &virtualmachines.ManagedDiskParameters{
		Id: pointer.To(existingDiskId),
	}
} else {
	osDisk.CreateOption = pointer.To(virtualmachines.DiskCreateOptionTypesFromImage)
	// ... set storageAccountType, diskEncryptionSet, etc.
}

// Assign to params
params.Properties.StorageProfile = &virtualmachines.StorageProfile{
	OsDisk: osDisk,
	// ...
}
```

### Verified Path

**When os_managed_disk_id is set:**
- `properties.storageProfile.osDisk.managedDisk.id` = disk ID
- `properties.storageProfile.osDisk.createOption` = "Attach"
- `properties.storageProfile.osDisk.caching` = required user input

**When os_managed_disk_id is NOT set (FromImage):**
- `properties.storageProfile.osDisk.managedDisk.storageAccountType` = user input
- `properties.storageProfile.osDisk.createOption` = "FromImage"
- Other fields like diskSizeGB, name, etc.

### Path Comparison

✅ **MATCH** - Implementation correctly places the field in `body.properties.storageProfile.osDisk` and conditionally sets either:
- Attach scenario: `managedDisk.id` + `createOption = "Attach"`

## Edge Case Analysis

### 1. Null Semantics

**Case:** `var.os_managed_disk_id = null`

**Behavior:** 
- Normal FromImage flow
- createOption = "FromImage"
- managedDisk.storageAccountType is used
- osProfile can be created (admin_username required)

**Edge Case:** User does not set os_managed_disk_id at all (default null)

**Behavior:** Same as explicit null - this is the standard VM creation from image scenario.

### 2. Empty String

**Case:** `var.os_managed_disk_id = ""`

**Behavior:** Since the variable is nullable and defaults to null, empty string is treated as a non-null value. The validation would pass (empty string != null), but Azure API would reject the invalid resource ID format.

**Safety:** This is acceptable per executor.md line 120 - resource ID format validations are skipped as they're verified by resource references.

### 3. Boundary Conditions

**Case:** os_managed_disk_id points to a disk in a different region

**Behavior:** Terraform plan succeeds, Azure API rejects at apply time with clear error message.

**Safety:** This is an Azure-level validation, not provider-level. We cannot replicate this without API calls.

**Case:** os_managed_disk_id points to a disk already attached to another VM

**Behavior:** Terraform plan succeeds, Azure API rejects at apply time.

**Safety:** This requires runtime Azure API state checking, which is beyond Terraform's static validation capabilities.

### 4. Idempotency

**Case:** Apply same configuration twice

**Behavior:** 
- First apply: Creates VM with attached disk (createOption="Attach")
- Second apply: No changes (disk ID hasn't changed)

**Safety:** ForceNew tracking ensures any change to os_managed_disk_id triggers replacement, maintaining consistency.

### 5. Safe References

**Implementation Check:**

```hcl

  managedDisk = {

  }
```

### 6. Interaction with os_disk.caching

**Case:** User sets os_managed_disk_id but forgets to set os_disk

**Behavior:** The existing variable definition requires os_disk to be provided when using the VM. The os_disk.caching field is Required in the os_disk block.

**Note:** Per the provider's description: "When using this field you must also specify `os_disk.caching`."

**Safety:** The existing os_disk variable validation enforces that caching must be provided, which handles this requirement.

### 7. Transition Scenarios

**Case:** Update VM to change from FromImage to Attach (or vice versa)

**Behavior:** ForceNew trigger causes VM replacement, which is correct - you cannot change the OS disk attachment method after creation.

**Safety:** This matches provider behavior exactly.
