## Special Handling

### 1. DiffSuppressFunc: suppress.CaseDifference

**Provider Implementation:**

The `suppress.CaseDifference` function is a built-in helper that suppresses diffs when two strings differ only in case. From the provider's comment:

```go
// the Compute/VM API is broken and returns the Resource Group name in UPPERCASE
// tracked by https://github.com/Azure/azure-rest-api-specs/issues/19424
```

**Why it exists:** Azure's Compute API has a known bug where it returns resource group names in uppercase in the response, even though the input used the correct case. Without suppression, every apply would show a case-only diff.

**Terraform Translation:**

According to `diffsuppressfunc.md`, I must:
1. Read existing state when the field is set
2. Compare lowercase versions of existing and desired values
3. If they match (case-insensitive), use the existing value (to preserve exact case from API)
4. Otherwise, use the desired value

**Implementation:**

```hcl
locals {
  should_read_existing_dedicated_host_id = var.dedicated_host_id != null

  existing_dedicated_host_id = local.should_read_existing_dedicated_host_id && data.azapi_resource.existing.exists 
    ? try(data.azapi_resource.existing.output.properties.host.id, null) 
    : null

  desired_dedicated_host_id = var.dedicated_host_id

  dedicated_host_id_should_suppress = (
    local.existing_dedicated_host_id != null &&
    local.desired_dedicated_host_id != null &&
    lower(local.existing_dedicated_host_id) == lower(local.desired_dedicated_host_id)
  )

  effective_dedicated_host_id = local.dedicated_host_id_should_suppress 
    ? coalesce(local.existing_dedicated_host_id, local.desired_dedicated_host_id) 
    : local.desired_dedicated_host_id
}
```

**Test Scenarios:**

**Scenario 1: Suppress case-only change**
- Existing: `/subscriptions/.../resourceGroups/MY-RG/providers/Microsoft.Compute/hostGroups/mygroup/hosts/myhost`
- Desired: `/subscriptions/.../resourceGroups/my-rg/providers/Microsoft.Compute/hostGroups/mygroup/hosts/myhost`
- Result: `dedicated_host_id_should_suppress = true`, uses existing value (preserves case from API)

**Scenario 2: Don't suppress actual change**
- Existing: `/subscriptions/.../resourceGroups/rg1/providers/Microsoft.Compute/hostGroups/group1/hosts/host1`
- Desired: `/subscriptions/.../resourceGroups/rg1/providers/Microsoft.Compute/hostGroups/group1/hosts/host2`
- Result: `dedicated_host_id_should_suppress = false`, uses desired value (triggers update)

**Scenario 3: Initial creation (no existing)**
- Existing: `null`
- Desired: `/subscriptions/.../resourceGroups/rg1/providers/Microsoft.Compute/hostGroups/group1/hosts/host1`
- Result: `dedicated_host_id_should_suppress = false`, uses desired value

### 4. Update Behavior - Requires Deallocation

**From Update method:**
```go
if d.HasChange("dedicated_host_id") {
    shouldUpdate = true

    // Code="PropertyChangeNotAllowed" Message="Updating Host of VM 'VMNAME' is not allowed as the VM is currently allocated. Please Deallocate the VM and retry the operation."
    shouldDeallocate = true

    if v, ok := d.GetOk("dedicated_host_id"); ok {
        update.Properties.Host = &virtualmachines.SubResource{
            Id: pointer.To(v.(string)),
        }
    } else {
        update.Properties.Host = &virtualmachines.SubResource{}
    }
}
```

**Analysis:**
- The field is NOT marked as `ForceNew: true` in schema
- The Update method CAN handle changes
- BUT changes require VM deallocation (`shouldDeallocate = true`)
- The AzureRM provider automatically deallocates, updates, and optionally restarts the VM

**Decision:**
The field is **updatable** in the provider (not ForceNew). The AzAPI provider will send update requests for this field, which is correct. However, users must manually deallocate the VM before updating this field, or they'll get an error from Azure API.

This is the EXACT behavior of the original field - it's updatable but requires deallocation. Since AzAPI doesn't have the automatic deallocation logic, users must handle this manually. This is a known limitation when migrating from azurerm to azapi.

**No ForceNew trigger needed** - the field is legitimately updatable in Azure API when VM is deallocated.
