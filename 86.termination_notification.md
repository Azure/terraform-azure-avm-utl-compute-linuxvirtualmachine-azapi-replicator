## Edge Case Analysis

### 1. Null Semantics

- **`var.termination_notification == null`:** Block not specified by user
  - Result: `terminateNotificationProfile.enable = false` (hidden default)
  - Meaning: "Disable termination notifications"
  
- **`var.termination_notification != null`:** Block specified by user
  - Result: Object with user-provided `enabled` and `timeout` values
  - Meaning: "Configure termination notifications per user input"

### 2. Merge Behavior

The skeleton uses `merge()` to combine `osImageNotificationProfile` and `terminateNotificationProfile` into a single `scheduledEventsProfile` object. This ensures:
- Both profiles coexist when both blocks are set
- Each profile can be independently configured
- No conflicts occur at the shared parent level

### 3. Boolean Default Logic

When the block is absent, the expand function explicitly sets `Enable: false`. This is different from:
- ❌ Omitting the field entirely (would be `null`)
- ❌ Sending no `terminateNotificationProfile` object (would be parent-level `null`)
- ✅ Always sending the object with `enable: false`

This ensures the API receives explicit "disabled" intent rather than "unspecified" intent.

### 4. Idempotency

The structure skeleton ensures idempotent behavior:
- First apply: Creates VM with `terminateNotificationProfile.enable = false` (if block absent)
- Subsequent applies: No changes detected (same structure sent each time)
- Adding block later: Updates from `enable: false` to user-specified values
- Removing block later: Updates back to `enable: false`

### 5. Safe References

The conditional uses `var.termination_notification != null` to check block presence before accessing nested fields. This is safe because:
- The variable is defined as `optional(object(...))` in variables.tf
- Terraform guarantees `null` when block not specified
- Child tasks will access fields only within the `!= null` branch
