### Issues Identified

#### Issue 1: Root-Level Default Value Missing `nullable = false`

**Problem:**
The `priority` variable in `variables.tf` had `default = null` but was missing the required `nullable = false` attribute. According to checker.md section 4.4.5, when a root/top-level argument has a default value in the provider schema, the variable definition MUST include both `default = value` AND `nullable = false`.

**Executor's Implementation:**
```hcl
variable "priority" {
  type        = string
  default     = null
  description = "(Optional) Specifies the priority of this Virtual Machine. Possible values are `Regular` and `Spot`. Defaults to `Regular`. Changing this forces a new resource to be created."

  validation {
    condition     = var.priority == null || can(regex("^(Regular|Spot)$", var.priority))
    error_message = "priority must be either 'Regular' or 'Spot'."
  }

  validation {
    condition     = var.priority != "Spot" || var.eviction_policy != null
    error_message = "eviction_policy must be specified when priority is set to 'Spot'."
  }
}
```

**Why This Violates executor.md:**
From executor.md lines 148-149:
> **Defaults:** If schema has `Default`, replicate it:
> - **Top-level:** `variable "field" { type = ...; default = value; nullable = false }` - **CRITICAL:** Root/top-level arguments with defaults MUST have both `default` value AND `nullable = false` set

From checker.md lines 402-434:
> **MANDATORY Check for Root/Top-Level Arguments with Defaults:**
> When a root/top-level argument has a default value in the provider schema, the variable definition MUST include:
> 1. ✅ `default = value` - matching the provider schema default
> 2. ✅ `nullable = false` - explicitly preventing null values

**Provider's Actual Behavior:**
```go
"priority": {
    Type:     pluginsdk.TypeString,
    Optional: true,
    ForceNew: true,
    Default:  string(virtualmachines.VirtualMachinePriorityTypesRegular),  // "Regular"
```

The provider schema has `Default: "Regular"`, which means:
- When user doesn't provide priority, provider uses "Regular"
- The field is never null in the provider's implementation
- Provider always sends this value to the API

**Expected Behavior:**
- Variable should have `default = "Regular"` (matching provider default)
- Variable should have `nullable = false` (preventing null override)
- This ensures users cannot explicitly pass `null` and bypass the default

**Root Cause:**
Executor used `default = null` instead of `default = "Regular"`, and omitted `nullable = false`. This allows users to override the default by explicitly passing `null`, which breaks the provider's guarantee that priority always has a value. The validation condition also incorrectly checked for `var.priority == null`, which should never be possible with proper defaults.

Additionally, the implementation used `coalesce(var.priority, "Regular")` in locals, which is a fallback approach when the PREFERRED approach (setting default directly in variable with nullable = false) was actually possible.
